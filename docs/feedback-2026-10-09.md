### Item 8: silent transmit

**Symptom.** Both nodes decoded KD2DCM-7's beacons but never each
other's packets. Between 20:43 and 20:56, -4 sent three messages to -3;
-3 decoded none of them although it was running. graywolf on both nodes
logged constant output errors, about 6,200 lines a minute at idle
(18,733 in a 3-minute capture at 21:54):

    cpal output stream error: ... get_htstamp ... was earlier than get_trigger_htstamp ...
    cpal output stream error: Buffer underrun/overrun occurred.
    cpal output stream failed, rebuilding

**Listening test (21:38-21:43, -3 sends to -7).** graywolf's own meter
showed clean tones at -7 dBFS peak, -10 dBFS RMS, no clipping. With
squelch open, -7 heard **only an open carrier, no audio**: PTT worked,
but the tones never reached the radio.

**Root cause: cpal 0.17.3 timestamp overflow on 32-bit ARM.** graywolf's
modem plays audio through the Rust library `cpal`, version 0.17.3 in the
0.14.14 release. In cpal 0.17.3's ALSA backend (`src/host/alsa/mod.rs`):

- `timespec_to_nanos` computes `tv_sec * 1_000_000_000 + tv_nsec` in the
  platform's `time_t`, which is 32 bits on 32-bit ARM (Pi Zero W). The
  product overflows after ~2 s of uptime and wraps.
- About half the time the wrapped "now" is less than the wrapped trigger
  time, so the check fails with "was earlier than", although the real
  time is later. Every logged value reproduces this:

| Logged pair | 32-bit nanoseconds | Result |
|---|---|---|
| 10971.497730 vs 10969.782785 | -2,143,711,280 vs 436,311,016 | negative: error |
| 5419.105150 vs 0.0 (10.0.1.183) | -1,143,577,552 vs 0 | negative: error |
| 12930.843616 vs 0.0 (21:54 capture) | -1,302,912,256 vs 0 | negative: error |

- The error returns from `process_output` **before** graywolf's audio is
  requested and **before anything is written to the sound card**. The
  card underruns, graywolf rebuilds the stream, and the cycle repeats. No
  audio is written while PTT is keyed: the silent carrier.

A 64-bit Pi OS likely never hits this (inference, not tested).

**Fix.** cpal 0.18.0 and later compute the callback timestamp without
failing. graywolf commit `4978244d` ("fix 32bit overflow bugs related to
cpal and alsa") moves to cpal 0.18.2; it is one commit after the 0.14.14
release, with no database changes.

- The maintainers' build `graywolf_0.14.14-4978244d_armv7l.deb` targets
  ARMv7 (`graywolf-modem` Tag_CPU_arch v7; `graywolf` GOARM=7) and would
  crash on the Pi Zero's ARMv6 CPU, so it was not installed.
- Rebuilt locally for ARMv6 the way graywolf's release workflow builds
  `arm-unknown-linux-gnueabihf` (cross-rs image, rustc 1.99.0, cpal
  0.18.2, patched alsa-rs `56099e8`; graywolf with `GOARM=6`):
  `graywolf_0.14.14+4978244d.armv6_armhf.deb`. Checked: Tag_CPU_arch v6,
  VFPv2, no ARMv7-only instructions.
- Installed 22:08 / 22:13: output errors went from ~3,400 a minute to 0,
  and -7 decoded -4. Receive still failed (item 10).

### Item 10: receive

**Small buffer.** With the cpal fix, input overran ~80 times a minute
and neither node decoded the other. Negotiated on 10.0.1.183
(`/proc/asound/card0/pcm0c/sub0/hw_params`): period 241 frames, buffer
482 frames at 48 kHz, **10 ms of slack**, capture and playback alike.
cpal 0.18.2's `BufferSize::Default` keeps the driver's period and rings
only 2 periods. Any process holding the single core for 10 ms drops
received audio. 24 kHz with this buffer made it worse (~25 to ~270-300
overruns a minute), so it was reverted at the time.

**Buffer fix: `gw_armv6` build.** A patch on top of `4978244d`
(`graywolf-armv6-audio-buffer.patch`, for the graywolf maintainers):

- `graywolf-modem/build.rs`: sets `cfg(gw_armv6)` only when `TARGET` is
  `arm-unknown-linux-gnueabihf`. Stable rustc has no ARM CPU-feature
  cfgs; ARMv6 and ARMv7 both report just `target_arch="arm"`.
- `audio/mod.rs`: `STREAM_PERIOD_FRAMES` is `Some(2048)` on `gw_armv6`,
  else `None` (driver default; other builds unchanged).
  `stream_buffer_size()` clamps it into the device's advertised range
  and falls back to `Default` when the device advertises none.
  `playback_ring_latency()` is 2 periods on ARMv6, zero elsewhere.
- `audio/soundcard.rs`: the runtime capture and playback streams use it
  and log "input/output buffer N frames/period"; the detection probe is
  unchanged.
- `modem/tx_worker.rs`: PTT stays keyed for the playback ring after the
  last sample is taken, so the end of the frame isn't cut. The existing
  "no artificial delay" test allows exactly that wait (and on ARMv6
  asserts it happens); a txdelay/txtail sleep still fails it.
- Tests: host 225 pass (the same 2 failures as unpatched source need a
  sound device / reference recording); ARMv6 under qemu 12/12, including
  a test that `gw_armv6` is set there.
- Package `graywolf_0.14.14+4978244d.armv6buf_armhf.deb` (SHA-256
  `a156ad83...58fe065`). Binaries: Tag_CPU_arch v6, VFPv2, no ARMv7-only
  instructions, glibc <= 2.16; both stamped `4978244d-armv6buf` so the
  running version shows it's patched.

**Demodulator too slow at 48 kHz.** With the buffer fix, input overruns
stopped, but the Pi Zero still decoded nothing. The modem's main thread
never once waited for audio (27 voluntary context switches in 9
minutes, 92% CPU): it was permanently behind, and its 64-chunk queue
dropped audio silently (`try_send`). The older builds only looked
cheaper (7%, 61%) because their audio streams kept failing.

**24 kHz with the fixed buffer** (period 2048, buffer 4096, ~170 ms):

| Node | Modem CPU | Waits for audio / 30 s | Input overruns |
|---|---|---|---|
| 10.0.1.183 | 46% | 1,450 (keeping up) | 0 |
| 10.0.0.65 | 46% | 1,403 (keeping up) | 0 |

**Two-way test, 23:12-23:14**, radios at low power in the same room:

- 23:12:30 -3 sent "cb test 4 from -3" (msg 019); -4 decoded it and
  sent `ack019`; -3 decoded the ack (23:12:37).
- 23:13:43 -4 sent "cb test 5 from -4" (msg 010); -3 decoded it and
  sent `ack010`; -4 decoded the ack (23:13:46).
- Both nodes decoded every KD2DCM-7 beacon in the window; -7 -> -4 at
  23:08:20 was decoded and acked.
- No input or output audio errors on either node. 10.0.1.183 shows 3
  bad-FCS frames since 22:53 (1 during the test), 10.0.0.65 none.

#### Pi Zero: setting graywolf's audio to 24 kHz

graywolf's web UI can't do this: Audio Devices → Edit only offers 8000,
16000, 44100 and 48000 Hz. graywolf's API accepts 24000, so set it from
a shell on the node (SSH), with the graywolf web login:

```sh
GW=http://127.0.0.1:8080
read -p 'graywolf user: ' U; read -s -p 'graywolf password: ' P; echo
J=$(mktemp)
printf '{"username":"%s","password":"%s"}' "$U" "$P" |
  curl -s -c "$J" -H 'Content-Type: application/json' --data-binary @- \
       -o /dev/null -w 'login: %{http_code}\n' "$GW/api/auth/login"
# Every AIOC device (input and output) -> 24000 Hz; other fields unchanged.
for id in $(curl -s -b "$J" "$GW/api/audio-devices" | python3 -c '
import sys, json
for d in json.load(sys.stdin):
    if "AllInOneCable" in d["device_path"]: print(d["id"])'); do
  curl -s -b "$J" "$GW/api/audio-devices/$id" | python3 -c '
import sys, json
d = json.load(sys.stdin)
keep = ("name", "direction", "source_type", "device_path", "channels", "format", "gain_db")
out = {k: d[k] for k in keep}
out["sample_rate"] = 24000
print(json.dumps(out))' |
  curl -s -b "$J" -X PUT -H 'Content-Type: application/json' --data-binary @- \
       -o /dev/null -w "device $id: %{http_code}\n" "$GW/api/audio-devices/$id"
done
rm -f "$J"
```

Expect `login: 200` and `device N: 200` for the input and the output.
graywolf applies the change at once; no restart is needed. Check:

- graywolf → Audio Devices shows "Sample Rate 24000 Hz" for both AIOC
  devices;
- `sudo journalctl -u graywolf -n 50 | grep "buffer 2048"` shows "input
  buffer 2048 frames/period" (the fixed-buffer build);
- `grep -E 'rate|period_size' /proc/asound/card0/pcm0c/sub0/hw_params`
  shows `rate: 24000` and `period_size: 2048`.

**Don't open Edit on these devices in graywolf's UI afterwards:** 24000
isn't in its list, so saving the dialog can reset the rate. If the
devices are edited or recreated, run the script again. To go back to
48 kHz (e.g. on a faster Pi), change `24000` to `48000` and run it again.

### Audio health metric (items 6 and 15)

Every failure in this round was audio lost between the sound card and
the demodulator, and most of it was invisible in the usual places:

| Where audio was lost | In the logs? | Shown by CPU %? |
|---|---|---|
| cpal skipping writes (silent carrier, item 8) | yes, error flood | no: modem at 7%, looked idle |
| ALSA overruns, 10 ms buffer (item 10) | yes, xrun lines | partly |
| Demodulator behind, queue dropping chunks (48 kHz) | **no, silent** | 92%, only a hint |

Ranked by reliability:

1. **Dropped audio (samples captured vs processed, plus overruns and
   queue drops).** Catches all three failures, traffic or not. graywolf
   doesn't count these today (a full queue is discarded silently).
2. **Demodulator keeping up (best available today).** Whether the
   modem's main thread ever waits for audio: its voluntary context
   switches in `/proc/<pid>/status`. 27 in 9 minutes = permanently
   behind (48 kHz); ~1,400 in 30 s = keeping up (24 kHz). Works with no
   traffic on air; reads the modem's process stats, not graywolf's API.
3. **Decode quality (end-to-end, needs traffic).** `rx_bad_fcs` vs
   `rx_frames` from graywolf's channel stats (a rising bad share means
   audio is lost or distorted), and acked messages / link checks.

Not reliable alone: CPU % (the broken build looked idle), input level
(proves only that the receiver is connected), and an error-free log
(queue drops never log).

**Recommendation:** the panel (item 15) and the status button (item 6)
show "modem keeping up: yes/no" and the bad-frame ratio.

### Item 15: CPU on the panel

Feasible: the panel already reads node facts itself (its network
addresses), and its systemd sandbox allows reading `/proc`. This is the
operating system's data, not graywolf's, so the API-only rule doesn't
apply. Proposal:

- The panel samples `/proc/stat` every ~10 s and keeps a 5-minute
  rolling average of total CPU busy %. The cost is a small file read.
- Shown in the footer next to the update time, e.g. "CPU 52% · 23:14".
  The panel redraws at most every 3 minutes, so the figure updates then.
- Above a threshold (say 80%) it also becomes a warning line ("! CPU 85%
  5 min"), which counts as a status change and triggers a redraw.

1. Total CPU only, or also the radio modem's share? The modem's share
   (from `/proc/<pid>/stat` of `graywolf-modem`) is what tells you
   whether receive keeps up, but it reads another program's process
   stats.
2. Is 80% the right warning threshold? On a Pi Zero at 24 kHz the
   normal total is roughly 55-65%.
3. Use the kernel's 5-minute load average (`/proc/loadavg`) instead?
   It's free to read but isn't a percentage: on the single-core Zero,
   above 1.0 means work is waiting.
